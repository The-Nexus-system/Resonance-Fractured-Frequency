RESONANCE: FRACTURED FREQUENCY
NATIVE iOS TRANSITION + REAL-WORLD SPATIAL GAMEPLAY DEVELOPMENT MASTER PROMPT

This is a controlled expansion of the EXISTING Resonance: Fractured Frequency project.

DO NOT replace, delete, rewrite, or damage the existing web application.

The existing web application is the validated playable reference build.

It has already passed the current beta accessibility gate for the playable four-puzzle First Fracture slice.

The web application must remain functional and independently playable throughout native iOS development.

We are now creating a SEPARATE NATIVE iOS CLIENT for Resonance.

The eventual goal is not merely to reproduce the web game on iPhone.

The native iOS application will become the foundation for a hybrid conventional + real-world game using Apple-native technologies including:

native iOS UI

IMPORTANT ARCHITECTURAL PRINCIPLE

There should not eventually be separate "blind gameplay," "Deaf gameplay," and "sighted gameplay" systems representing different worlds.

There should be ONE underlying Resonance world state.

The same game object/event may then have:

a visual/AR representation,
a 3-D spatial-audio representation,
a haptic representation,
a caption/text representation,
and an accessibility/screen-reader/braille representation.

These representations must describe the SAME underlying object, location, state, and event.

Accessibility is part of the game architecture.

It is not a later compatibility layer.

==================================================
PHASE 4 — 3-D SPATIAL AUDIO PROTOTYPE
==================================================

3-D spatial audio is a CORE GAMEPLAY SYSTEM.

It is not decorative sound.

Create a controlled prototype environment using local/test objects before introducing real GPS locations.

A player must be able to determine through spatial audio:

whether an object is left or right,
ahead or behind where technically reliable,
approaching or receding,
near or far,
and when the object enters interaction range.

Where vertical position matters and can be communicated reliably, test vertical differentiation.

Create clear audio categories for:

navigation,
mission objectives,
interactable objects,
hazards,
characters,
companions,
environment,
vehicles/craft,
equipment,
and decorative ambience.

Do not make every object beep.

Create an audio hierarchy.

Important information must remain distinguishable from ambience and music.

==================================================
REAL-WORLD ENVIRONMENTAL AUDIO PRIORITY
==================================================

Real-world safety takes priority over game audio.

The game must support dynamic audio mixing appropriate for real-world travel.

When environmental awareness becomes important:

reduce or duck:

music,
decorative ambience,
nonessential dialogue,
nonessential game sounds.

Preserve only appropriate critical game information.

The game must NEVER intentionally mask:

traffic,
crossing signals,
human warnings,
service-animal information,
mobility cues,
emergency announcements,
or other important environmental information.

The game is NEVER an authority on whether crossing a street, entering an area, or performing a physical action is safe.

==================================================
PHASE 6 — SEMANTIC INTERACTION SYSTEM
==================================================

Create ONE underlying interaction command:

INTERACT WITH NEAREST ELIGIBLE TARGET

The mechanic is NOT "shake the phone."

Shake is ONE input method for issuing the semantic interaction command.

Supported interaction pathways should eventually include where technically appropriate:

shake,
accessible on-screen control,
VoiceOver accessibility action,
Switch Control,
Voice Control,
connected keyboard,
controller,
and other appropriate accessible input.

All input methods call the same underlying interaction logic.

==================================================
SHAKE TO INTERACT
==================================================

Implement configurable shake-to-interact.

Example:

A Resonance object enters the player's interaction envelope.

The player deliberately shakes the phone.

The game determines the nearest eligible target inside the interaction envelope.

If exactly one eligible target exists:

perform the appropriate contextual interaction.

Examples:

collect,
scan,
activate,
acknowledge,
stabilize,
open,
communicate,
or perform the object's established contextual action.

Immediately provide multimodal confirmation.

If multiple eligible objects exist:

DO NOT randomly choose unless game rules explicitly permit automatic priority.

Tell the player that multiple signals/objects are available and provide an accessible selection mechanism.

If no eligible object exists:

provide brief understandable feedback.

Do not punish the player.

==================================================

Do not require coordinate precision.

Initial prototype interaction distance may begin around approximately TWO METRES for appropriate stationary/walking encounters, but this must be configurable and tested.

The game must account for:

GPS drift,

construction,
temporary barriers,
private property,
inaccessible terrain,
mobility-device turning radius,
service-animal routes,
orientation-and-mobility techniques,
and other real-world accessibility factors.

The important concept is:

REACHABLE PROXIMITY

not:

EXACT COORDINATE MATCH.

==================================================
CORE REAL-WORLD RULE
==================================================

RESONANCE OBJECTS COME TO THE PLAYER'S ACCESSIBLE TRAVEL CORRIDOR.

THE PLAYER IS NOT REQUIRED TO LEAVE THEIR SAFE TRAVEL CORRIDOR FOR RESONANCE OBJECTS.

If an encounter would require:

crossing unnecessarily,
climbing inaccessible stairs,
entering unsafe terrain,
entering private property,
leaving a known accessible route,
or making another unreasonable physical detour,

the interaction point should be relocatable or the encounter should not be offered there.

PHASE 8 — REAL-WORLD ROUTE-AWARE GAMEPLAY
==================================================

After local spatial interaction works, begin Core Location integration.

The design target is:

A player is already going somewhere.

Examples:

walking to a store,
rolling to work,
taking a bus,
riding in a car,
traveling by train,
moving through a station,
going to an appointment,
or taking another ordinary journey.

Resonance transforms appropriate portions of that EXISTING journey into gameplay.

The game should not normally require players to make unsafe or unnecessary detours simply to collect an object.

Where technically and legally appropriate, create a route/travel corridor.

Eligible Resonance encounters can be selected or positioned within accessible interaction opportunities along that corridor.

==================================================
PHASE 9 — TRAVEL STATE
==================================================

Do NOT assume that vehicle movement means the user is driving.

Support conceptual travel states including:

STATIONARY
WALKING/ROLLING
PASSENGER
DRIVER
UNKNOWN

Do not infer DRIVER solely because the device is moving at vehicle speed.

Passengers are legitimate players.

Passenger gameplay may include:

pass-by collection,
signal interception,
scanning,
communications,
resource collection,
mission observation,
and other low-risk interactions.

If the system cannot reliably distinguish driver from passenger:

default to conservative behavior.

Do not encourage active interaction from someone who may be driving.

Provide a way for the player to explicitly indicate passenger status where appropriate, while still designing conservatively.

==================================================
PASSENGER INTERACTION
==================================================

A two-metre interaction radius is inappropriate for a moving vehicle.

Passenger encounters should use a larger contextual capture/interception window.

Example:

A Resonance signal is approaching along the travel corridor.

The game provides an appropriate spatial-audio/haptic/text/visual warning.

The object enters the passenger interaction window.

The passenger may issue INTERACT WITH NEAREST ELIGIBLE TARGET using shake or another accessible input.

The game resolves the encounter.

Missing the encounter must not encourage dangerous behavior.

Do not instruct players to:

turn the vehicle around,
exit unexpectedly,
cross traffic,
return to an unsafe location,
or pressure a driver to change course.

==================================================
PHASE 10 — STATIONARY OPPORTUNITY GAMEPLAY
==================================================

Use naturally stationary moments as potential opportunities for richer interactions.

Examples may include:

waiting for transit,
sitting in a safe location,
waiting in a queue,
waiting for another person,
or being otherwise stationary.

A stop at an intersection may create a potential gameplay opportunity ONLY if it can be done without interfering with real-world navigation.

THE GAME MUST NEVER SAY OR IMPLY THAT IT IS SAFE TO CROSS.

The player's:

orientation and mobility skills,
service animal,
accessible pedestrian signal,
traffic assessment,
human assistance,
and other real-world safety systems

remain authoritative.

Resonance is gameplay.

It is not a mobility aid or crossing-safety authority.

==================================================
PHASE 16 — NONVISUAL REAL-WORLD PLAYTHROUGH
==================================================

For every implemented real-world prototype, test without relying on graphics.

Ask continuously:

Where is the target?

How far away is it?

What direction is it?

Is it approaching?

Is it leaving?

Is it in interaction range?

What type of object is it?

What action is available?

Did my interaction succeed?

What changed?

What should I do next?

Can I recover if I become disoriented?

Can I continue without looking at the screen?

If required information cannot be determined nonvisually:

treat that as an accessibility blocker.

==================================================
PHASE 18 — CROSS-MODAL STATE CONSISTENCY
==================================================

For every significant real-world game object/event compare:

WHAT THE AR PLAYER SEES

WHAT THE SPATIAL-AUDIO PLAYER HEARS

WHAT THE HAPTIC SYSTEM COMMUNICATES

WHAT VOICEOVER/BRAILLE COMMUNICATES

WHAT CAPTIONS/TEXT COMMUNICATE

WHAT THE GAME STATE ACTUALLY SAYS

These must describe the SAME event.

Example:

If a fragment is 1.5 metres to the player's right and eligible for collection:

AR must render the corresponding object appropriately.

Spatial audio must represent the corresponding direction/distance appropriately.

Haptics must communicate interaction availability according to the established vocabulary.

VoiceOver/braille must expose the relevant state.

The interaction command must target that SAME object.

Successful collection must remove/change that SAME object across every representation.

Fix inconsistencies at the shared state/event layer rather than creating unrelated modality-specific hacks whenever possible.

PHASE 19 — REAL-WORLD SAFETY RULES
==================================================

Real-world gameplay must NEVER reward unsafe behavior.

Do not incentivize:

running into traffic,
crossing against signals,
entering private property,
entering dangerous terrain,
using inaccessible routes,
climbing structures,
approaching hazards,
interacting while driving,
ignoring a service animal,
ignoring environmental warnings,
or physically exceeding a player's capabilities.

Do not create essential limited-time collectibles that pressure someone into unsafe movement.

Missed real-world encounters should generally be recoverable, repeatable, replaceable, or nonessential.

Main story completion must not depend upon performing an unsafe physical-world action.

==================================================

Do not collect or retain unnecessary:

mobility patterns,
or other sensitive information.

Clearly separate:

information required for gameplay,
temporary sensor processing,

Do not silently expand data collection merely because native APIs make it possible.

==================================================
FINAL PRINCIPLE
==================================================

The goal is not:

"Pokémon Go with accessibility added."

The goal is a native spatial game whose underlying mechanics were designed from the beginning for players with different sensory, cognitive, communication, and mobility needs.

A sighted player may discover Resonance through AR.

A blind player may discover the same Resonance object through 3-D spatial audio and haptics.

A Deaf player may discover the same object through AR, text, and haptics.

A DeafBlind player may use braille, haptics, accessible controls, and other supported representations.

A wheelchair user may encounter it along their accessible route without being required to stand or walk.

A vehicle passenger may intercept it while traveling without being treated as the driver.

These players are interacting with the SAME GAME OBJECT and the SAME WORLD.

The real world remains authoritative for safety.

Resonance adapts to the player's journey.

The player should not be required to make their journey unsafe in order to adapt to Resonance.

BEGIN NOW WITH PHASE 0.

Preserve and verify the current web build first.

Then create the separate native iOS architecture and proceed through the phases in order.

Do not begin broad AR/location feature development until native parity with the existing playable slice has passed.
