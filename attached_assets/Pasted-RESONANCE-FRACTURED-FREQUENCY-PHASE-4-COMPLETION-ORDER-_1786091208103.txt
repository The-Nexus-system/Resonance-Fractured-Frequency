1. FINISH THE REAL 3-D WORLD RENDERER
    ==================================================

Build an actual reusable 3-D presentation layer over the existing semantic spatial world model.

The semantic spatial model remains the single source of truth.

The 3-D renderer must consume semantic entities from that model.

It must NOT create a second independent representation of:

* Object identity
* Position
* Orientation
* Discovery
* Reachability
* Interaction state
* Puzzle state
* Attunement state
* Rewards
* Canonical progression

A semantic object should be able to be represented simultaneously through:

* 3-D graphics
* AR
* Spatial audio
* VoiceOver
* Braille-compatible semantic text
* Captions
* Haptics

without becoming separate versions of the object.

Create reusable 3-D entity/component architecture suitable for later campaigns.

* World-space position

* Elevation
* Visibility
* Discovery state
* Interaction state
* Animation state
* Resonance state

Do not hard-code the renderer specifically around the eleven First Fracture objects.

The current camera overlay is useful and should remain available if appropriate, but it is not the final AR implementation.

Implement actual native world-space AR using supported iOS technology such as RealityKit / ARKit where appropriate.

Objects should occupy positions in the AR world rather than simply appearing as directional 2-D overlays.

The AR system should support, where device capability permits:

* Stable world-space placement
* Position relative to the player
* Distance
* Elevation
* Orientation
* Occlusion or depth behavior where safe and performant
* Looking around with the device
* Moving closer to or around an object
* Selecting an object visually
* Tapping an AR object to invoke its semantic interaction

The AR renderer remains OPTIONAL.

Camera permission denial must never block completion.

AR tracking failure must never corrupt game state.

The game must remain fully playable:

* Without camera permission
* Without AR support
* While stationary
* With VoiceOver
* With sound disabled
* With haptics disabled
* With both sound and haptics disabled

Do not require walking to complete The First Fracture.

Physical movement may enrich the experience but cannot be required.

3. GIVE THE FRACTURE A FINISHED VISUAL IDENTITY

The existing double-ring / steady-ring indicators are useful accessible state indicators, but they are not sufficient as the final graphical presentation.

Build a richer visual language appropriate to a polished commercial-quality game.

The visual treatment should make a FRACTURED environment visibly feel unstable and an ATTUNED environment visibly feel changed.

Do not simply add generic glowing sci-fi objects.

Develop a coherent visual language for Resonance.

Possible techniques include:

* Geometric distortion
* Slight spatial duplication
* Broken symmetry
* Phase-like offset copies
* Ripple propagation
* Particle displacement
* Surface warping
* Fragmented light
* Chromatic separation
* Refraction-like effects
* Wave patterns
* Harmonic pulse animations
* Distorted environmental geometry
* Unstable shadows or light response
* Resonance fields
* Object-specific visual signatures
* Environmental effects that stabilize as progress is made

Use judgment and build a coherent combination rather than applying every effect everywhere.

The graphics should communicate:
“This place is fractured.”

Then, through player action:
“This place is becoming coherent.”

When all four main resonators are restored, the environment should have a meaningful visual transformation, not merely four objects changing icons.

Examples could include:

* Environmental distortion settling
* Particles synchronizing
* A fractured light pattern resolving
* Previously unstable geometry becoming coherent
* Resonance waves synchronizing through the environment
* The beacon or central field becoming visually whole

Do not rely solely on color.

State must continue to be communicated through:

* Shape
* Motion
* Texture
* Text
* Semantic description
* Audio where enabled
* Haptics where enabled

Reduce Motion must continue to work.

When Reduce Motion is enabled, replace movement-heavy effects with meaningful static alternatives rather than simply removing information.

6. UPGRADE SOUND DESIGN BEYOND BASIC SYNTH TONES

The F–A–C–high-F harmonic structure is GOOD and should remain.

However, the final experience should not sound like four basic oscillator test tones.

Keep the harmonic architecture but develop richer sound identities.

Each resonator should have a recognizable musical voice.

For example:

LOW F RESONATOR
A warm, low foundation.
It might combine a soft fundamental, subtle harmonic texture, low resonant body, and environmental resonance.

A RESONATOR
A warmer middle voice.
Potentially bell-like, bowed, glassy, vocal-like, or another appropriate timbre.

C RESONATOR
A steadier rhythmic or structural voice.
It may carry subtle pulse or percussive identity without becoming irritating.

HIGH F RESONATOR
A bright upper voice.
Shimmer, air, high harmonic movement, or another identifiable texture.

These are descriptions of intent, not rigid instrumentation requirements.

The important properties are:

* They sound distinct.
* They belong to the same musical world.
* They combine musically.
* They can exist for extended play without becoming irritating.

Broken resonators should sound fractured.

Possible techniques include:

* Controlled detuning
* Beating
* Interrupted harmonics
* Phase drift
* Granular instability
* Uneven pulse
* Incomplete harmonic content
* Filter instability
* Spatial instability

Attuning should audibly restore coherence.

The transformation should happen musically rather than simply replacing a “bad sound” with a “good sound.”

7. MAKE THE ENVIRONMENT ITSELF MUSICAL

Do not limit musical change to the four individual resonators.

Build support for an environmental music system that responds to world state.

The First Fracture should be capable of evolving as resonators are restored.

Example conceptual progression:

0 restored:
Sparse, unstable, fractured atmosphere.

1 restored:
One stable musical voice joins the world.

2 restored:
Harmony begins to emerge.

3 restored:
The environment is clearly approaching coherence.

4 restored:
The F-major structure resolves and the entire environment feels musically whole.

Do not require players to know what F major means.

A nonmusician should experience:
“The world just came together.”

Every meaningful sound change must continue to have useful captions and semantic descriptions.

Avoid captions that merely say:
“Music plays.”

Prefer meaningful descriptions such as:
“A warm low resonance settles into tune beneath the fracture.”

Do not overload captions with music-theory terminology.

8. FINISH THE SEMANTIC INTERACTION INPUT SYSTEM

The current button and optional shake gesture are only part of the requested input architecture.

There must be ONE semantic action system underneath multiple input mechanisms.

Inputs must not duplicate gameplay logic.

For example:

Interact(objectID)

or equivalent semantic architecture.

That same action should be callable through all appropriate supported methods.

Implement and test the following where supported:

A. ON-SCREEN ACTION

Keep a large, accessible Interact / Collect / Attune button.

Stationary play must always have this option.

B. AR OBJECT TAP

A sighted player should be able to tap a rendered AR object.

The tap must invoke the SAME semantic object action as the accessible button.

Do not create separate AR-specific puzzle logic.

C. VOICEOVER

Expose meaningful semantic objects to VoiceOver.

Where appropriate, provide UIAccessibilityCustomAction-style actions such as:

* Inspect
* Interact
* Collect
* Attune
* Ping

Do not force a VoiceOver player to locate a tiny visual target.

The accessibility action must invoke the same semantic action as every other input.

D. HARDWARE ACTION BUTTON

Investigate and, where legitimately supported, implement an iPhone Action Button route for the current contextual game action.

Do not assume every iPhone has an Action Button.

The app must remain fully functional without it.

The Action Button should ideally invoke the currently available semantic action, not contain separate gameplay logic.

If direct Action Button integration requires App Intents, Shortcuts, Controls, or another supported Apple mechanism, use the legitimate supported architecture.

Document exactly what was possible.

E. BACK TAP

Investigate a legitimate supported method for allowing a user to invoke the game’s contextual interaction through iOS Back Tap.

Do NOT use private APIs.

Do NOT claim the app can receive the system Back Tap gesture directly unless Apple provides a supported mechanism.

A likely legitimate architecture may involve:

* App Intents
* Shortcuts
* Accessibility Shortcut behavior
* Another supported system action

If the user can assign an app-provided action to iOS Back Tap, implement the app side required to make that possible.

If iOS does NOT provide a supported route, state that clearly in the final report.

Do not fake completion.

F. SHAKE

Keep optional shake-to-interact.

It remains OFF by default.

Retain debounce/rapid-repeat protection.

G. STATIONARY INPUT

A stationary user must be able to perform every required action without:

* Shaking
* Walking
* Camera
* Hardware Action Button
* Back Tap
* Physical device movement
